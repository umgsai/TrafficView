# TrafficView M5 发布与兼容工具 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 交付 TrafficMonitor 皮肤转换器、可复现性能基准、deb/rpm/AppImage 和完整用户/发布文档。

**Architecture:** 转换器复用 M2 的 `Skin` 校验与渲染预览，避免形成第二套布局语义。打包只组装已测试的 release 二进制、user service 和桌面前端；可选 GTK settings 与特权 netprobe 分包，主包保持无 GTK/Qt/libdbus/eBPF 依赖。

**Tech Stack:** M4 + quick-xml、configparser、cargo-deb、cargo-generate-rpm、appimagetool、Criterion、hyperfine/pidstat、SHA-256。

**前置条件:** M4 完成；目标发行版干净 VM 可用。项目所有者必须提供正式 `LICENSE` 才能发布，计划不擅自选择许可证；若 LICENSE 缺失，打包测试可继续但公开发布必须停止。

- [ ] **Step 1: 写 INI、XML 和图像迁移失败测试**

每种 fixture 包含背景、net_up/net_down/cpu/mem、rect、字体、颜色、对齐和 format。测试转换后再调用 M2 `Skin::load` 和离屏 preview，确保转换结果不是只能序列化但不能渲染。

```rust
#[test]
fn ini_layout_semantics_match_native_skin() {
    let report = convert_trafficmonitor(fixture_path("trafficmonitor-ini"), output.path()).unwrap();
    let native = Skin::load(output.path()).unwrap();
    assert_eq!(native.item("net_up").unwrap().rect, [10, 6, 92, 20]);
    assert_eq!(native.item("net_down").unwrap().align, Align::Right);
    assert!(output.path().join("background.png").is_file());
    assert!(report.warnings.is_empty());
}

#[test]
fn xml_and_ini_produce_equivalent_layouts() {
    let ini = convert_trafficmonitor(fixture_path("trafficmonitor-ini"), ini_out.path()).unwrap();
    let xml = convert_trafficmonitor(fixture_path("trafficmonitor-xml"), xml_out.path()).unwrap();
    assert_eq!(Skin::load(ini_out.path()).unwrap(), Skin::load(xml_out.path()).unwrap());
}
```

补充 BMP→PNG alpha、未知 Windows item、缺少背景、非法 rect、绝对路径、`../` 路径穿越、输出目录已存在和 `--force` 原子替换测试。Windows 专用插件 item 映射为 warning，不生成伪造内置指标。

- [ ] **Step 2: 确认失败**

Run: `cargo test -p trafficview-render --test trafficmonitor`

Expected: FAIL，转换模块和 fixtures 尚未实现。

- [ ] **Step 3: 实现 AST 转换与 CLI**

转换流程固定为：识别 `skin.ini`/`skin.xml` → 解析为中间 `TrafficMonitorSkin` → 逐项映射内置 id → 转换 rect/font/color/align/format → 背景 PNG 保留、BMP 解码后编码 PNG → 生成 `skin.toml` → 调用 `Skin::validate` → 临时目录 rename 到输出。任何失败都不留下半套皮肤。

CLI：

```text
trafficview skin convert <trafficmonitor-skin-dir> --output <native-skin-dir> [--force]
```

stdout 输出 JSON 报告，字段为 `output/items_converted/items_skipped/warnings`；警告写报告而非静默丢弃。未加 `--force` 时输出存在即失败。转换器只读本地输入，不联网、不执行皮肤内任何命令。

- [ ] **Step 4: 验证迁移与 X11/Wayland 渲染**

Run: `cargo test -p trafficview-render --test trafficmonitor && cargo test --workspace`

Expected: 全部 PASS；INI 与 XML fixture 的原生预览像素语义一致，在 X11 与 KDE/Wayland 加载后 rect、颜色和背景一致。

- [ ] **Step 2: 运行基准并确认 harness 可用**

Run: `cargo bench --workspace --no-run`

Expected: 初次因 bench target 不存在或 Criterion 未配置而 FAIL；添加 harness=false 和 bench 文件后同一命令 PASS。

- [ ] **Step 3: 实现基准和发布构建脚本**

`build-release.sh` 使用 `set -euo pipefail`，先跑测试再构建：

```bash
#!/usr/bin/env bash
set -euo pipefail
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --workspace --release
mkdir -p dist
cp target/release/trafficview target/release/trafficviewd dist/
sha256sum dist/trafficview dist/trafficviewd > dist/SHA256SUMS
```

Criterion 分别测格式化、proc 解析、单帧渲染、SQLite 分钟/日查询。保存基准到 gitignored 的 `target/criterion`，不提交机器相关的性能数字作为源码。

- [ ] **Step 4: 测量真实资源预算**

在固定目标 Linux 机器、1 秒采样、默认皮肤、无 eBPF 下运行：

```bash
trafficview status --format json > /tmp/trafficview-snapshot.json
hyperfine --warmup 5 --runs 30 'trafficview status --format json'
pidstat -p "$(pidof trafficviewd)" 1 60
pidstat -r -p "$(pidof trafficviewd)" 1 60
/usr/bin/time -v trafficview skin preview crates/render/tests/fixtures/minimal --snapshot /tmp/trafficview-snapshot.json --output /tmp/trafficview-bench.png
cargo bench --workspace
```

Expected: daemon 稳态 CPU 平均 <0.3%、daemon+默认前端 RSS <30MB、正常每秒一次唤醒；启动延迟用独立 `trafficviewd`/D-Bus readiness 测量 <80ms。若不达标，先建立可复现 profile，再做最小优化并重跑全部正确性测试，不放宽预算来隐藏回退。eBPF 模式另测 <1% CPU。

- [ ] **Step 1: 写包内容检查清单和依赖失败测试**

构建脚本在任何包生成前验证 release 二进制存在且非空，`ldd` 输出不包含 GTK、Qt、libdbus、libX11（x11rb 使用纯 Rust 协议栈）或 NVML 的硬依赖。NVML 必须运行时动态发现。主包包含：

```text
/usr/bin/trafficview
/usr/bin/trafficviewd
/usr/lib/systemd/user/trafficviewd.service
/usr/share/applications/trafficview.desktop
/usr/share/doc/trafficview/...
```

GNOME/Plasma 前端作为推荐子包，settings 作为可选包，netprobe 作为独立可选特权包；卸载主包不得删除用户 `~/.config` 或 `~/.local/share/trafficview/history.db`。

- [ ] **Step 2: 配置并运行打包工具**

使用 cargo-deb 与 cargo-generate-rpm 的显式 assets，不能依赖执行者当前目录：

```bash
cargo deb -p trafficview-cli --no-build --output dist/trafficview_amd64.deb
cargo generate-rpm -p trafficview-cli -o dist/trafficview.x86_64.rpm
```

AppImage 的 `AppRun` 只设置应用私有资源路径并 exec `usr/bin/trafficview`，不修改系统 `LD_LIBRARY_PATH`；daemon 子命令路径通过同目录解析。用 appimagetool 生成 `dist/TrafficView-x86_64.AppImage`，所有包名版本从 workspace version 派生，不手写第二份版本。
